# 发布流程

推送 `v*` 标签后，GitHub Actions（`.github/workflows/release.yml`）先运行全部单元测试，通过后构建五个签名 APK（四个 ABI 分包与通用包），校验通过后上传到该标签的 Release 草稿。更新说明仍由人工撰写，草稿发布前应用内更新检查不到新版本。

## 首次配置

1. 仓库 **Settings → Environments → New environment**，名称填 `release`。
2. **Deployment branches and tags** 选择 **Selected branches and tags**，添加标签规则 `v*`；若需要从 `main` 手动试跑，再添加分支规则 `main`。不在规则内的分支和标签读取不到该环境的密钥。
3. 在 `release` 环境中添加以下 secret：

   | Secret | 内容 |
   |---|---|
   | `RELEASE_KEYSTORE_BASE64` | 发布密钥库文件的 Base64 |
   | `RELEASE_STORE_PASSWORD` | 密钥库密码 |
   | `RELEASE_KEY_ALIAS` | 密钥别名 |
   | `RELEASE_KEY_PASSWORD` | 密钥密码 |

   在 PowerShell 中将密钥库转为 Base64 并复制到剪贴板：

   ```powershell
   [Convert]::ToBase64String([IO.File]::ReadAllBytes("D:\path\to\release.jks")) | Set-Clipboard
   ```

4. 在 **Actions → Release → Run workflow** 中选择 `main` 试跑。成功即说明密钥配置正确，生成的 APK 可在该次运行页面下载，保留 7 天。

## 发布新版本

1. 修改 `app/build.gradle.kts` 中的 `appReleaseVersionCode` 与 `appReleaseVersionName`，提交并推送，等待该提交的 CI 通过。
2. 为该提交打标签并推送，标签必须是 `v` 加 `versionName`：

   ```bash
   git tag v3.3
   git push origin v3.3
   ```

3. 工作流完成后，在 Releases 页面编辑草稿，填写更新说明并发布。

同一标签重新运行工作流时，会覆盖该 Release 中的安装包。

## 构建校验

- 构建前运行的单元测试与日常 CI（`.github/workflows/ci.yml`）相同，未全部通过时不构建安装包，也不会创建 Release 草稿。测试失败时，可在该次运行页面下载测试报告。
- 标签与 `versionName` 不一致时构建失败。应用内更新按标签版本号匹配安装包文件名，两者不一致会导致用户无法下载更新。
- 每个 APK 的签名证书 SHA-256 必须与历届正式版一致，否则构建失败，避免误配密钥导致用户无法覆盖安装。若更换签名密钥，需同步修改工作流中的 `RELEASE_CERT_SHA256`。

## 本地签名

`app/build.gradle.kts` 仅在设置了 `BILITOOLS_RELEASE_STORE_FILE` 等环境变量时创建 `release` 签名配置。本地仍可通过 Android Studio 的 **Build → Generate Signed App Bundle or APK** 签名，流程不变。
